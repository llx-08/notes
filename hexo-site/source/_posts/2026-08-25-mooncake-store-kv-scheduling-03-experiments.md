# 03 · 实验编年史

这一章按时间顺序记录，**包括被推翻的结论和推翻它们的证据**。只留最终版本的话，
下次还会踩同样的坑——这个项目最大的教训不是某个数字，而是错误是怎么产生并被识破的。

![结论演化](/imgs/mcstore_conclusion_evolution.svg)

## 负载：真实 agentic trace

`replay_trace.py` 重放 `Inferact/codex_swebenchpro_traces`（218 MB，610 个 trial）。
选它的两个理由：

- **每个 trial 共享一段很长的系统前缀**，所以不同 trial 能命中彼此的缓存——这正是共享 store 的用武之地
- **同一 trial 相邻两次调用间隔数秒**（数据集卡片给的中位数 5.2s），
  这给异步 store 写入留出落地时间

一个术语：**一个「臂」（arm）= 一个受控条件下的一次完整运行** = 24 trial × 最多 24 轮
= 433 个请求，墙上时间约 285 秒。

**salt 隔离**是关键机制：salt 插在 prompt 最开头，而 block hash 是从开头链式计算的，
所以换 salt 等于把整臂运行搬进一个**独立的 key 命名空间**。这样两个策略可以跑完全相同的 trial
（样本量、prompt 总量一致），又不会互相预热缓存。代价是每臂都要往 store 里写一份全新的 KV。

## 阶段一：Qwen3-32B，结论被推翻两次

同一个 `prefix_affinity` 策略，三轮实验分别是**落后 37% → 领先 27% → 领先 7%**，
而这三个数字的差异**全部来自基础设施缺陷**：

| 轮次 | 结果 | 真实原因 |
|---|---|---|
| 跨机单网卡 | 领先 27% | 7 个 P 挤一张 `mlx5_bond_0`，store 读被单口带宽卡住，虚高了「避免走 store」的价值 |
| 跨机多网卡 | 落后 37% | 绝对护栏在低并发下从不触发，流量雪球到单节点（43 vs 7），排队惩罚超过省下的传输时间 |
| 修好护栏 | 领先 7% | 护栏改成「衰减累积分配量的相对阈值」`load_ratio ≈ 1.5` |

第二轮那次「落后 37%」的按轮次延迟曲线很有诊断价值：

```
绝对护栏:  4466 → 2766 → 2676 → 2623 → 2844 → 3148 → 3453 → 2373   先降后升
修好之后:  2478 → 1801 → 1849 → 1715 → 1666 → 1644 → 1675 → 1660   单调下降后持平
```

**第 4 轮起的回升**就是流量雪球堆到单节点、缓存互相踩踏的信号。

同时还有一个反直觉观察：`avg_match = 162` chunks（≈83k 字符）说明**亲和识别从头到尾都很准**。
**识别准 ≠ 跑得快。**

## 阶段二：读 dashscope 网关

发现网关早有成熟实现，搬了两个机制回来：几何 key 生成、指数打分（详见 [02 章](/notes/2026/08/25/2026-08-25-mooncake-store-kv-scheduling-02-scheduler-design/)）。

## 阶段三：几何网格 A/B 无害性验证

**这一步的目的不是求收益，是确认改动没弄坏排序能力。** 因为我改了打分的量纲
（chunk 个数 → 匹配字符数），必须先证明它无害。

同一批 trial、同 `load_ratio=1.5`：

| | 线性 512 | 几何 k=4 |
|---|---|---|
| p50 | 1706.4 ms | 1693.8 ms |
| p90 | 2383.4 ms | 2404.2 ms |
| 本地 HBM / store / 重算 | 75% / 2% / 23% | 75% / 2% / 23% |
| **决策** | miss 1, hit 118, 让位 22 | **miss 1, hit 118, 让位 22** |
| 每请求 key（26k） | 152 | **20** |

**141 个决策一字不差地相同。** 换网格没有损失任何排序能力，延迟差异在噪声内。

## 阶段四：指数打分 K 扫描

| | 基线 硬阈值 | K=10 | K=5 | K=2.5 |
|---|---|---|---|---|
| p50 | **1694** | 1708 | 1724 | 1749 |
| 本地 HBM | **75%** | 69% | 66% | 60% |
| store | 2% | 6% | 10% | 13% |
| routes 最多/最少 | 26/15 | 25/15 | **22/18** | **21/18** |
| 采样命中 argmax | — | 0.745 | 0.702 | 0.766 |

指数打分更平衡，但**丢本地命中**：采样有 25~30% 概率不选 argmax，
每次偏离就把一个本地命中换成 store 读。

于是加了一档「固定 K、把绝对幅度放大 4 倍」（40/4）让采样趋近确定性。
首次测出 p50 1635 ms（−3.5%）、**重算 3%**——看起来赢了。

## 阶段五：关键订正 —— store 常驻驱逐污染了整个阶段一

`重算 3%` 触发了警报，因为它**低于理论下界**：

```
N 轮会话：所有 prompt 之和 = N(N+1)/2 单位，真正新增 = N 单位
       → 重算下界 = 2/(N+1)
8 轮 → 22%（其余各轮实测 23% ✓）    3% 物理上不可能
```

重跑验证：基线复现良好（1705 ms / 74% / 2% / 23%），**sharp 那档不复现**
（1700 ms / 76% / **1%** / **23%**）。查 store 状态找到根因：

```
占用       88.5% 89.8% 87.3% 85.7% 87.7% 87.0% 87.8% 88.6% 90.0% 86.7%
累计驱逐    3     3     7     11    14    18    28    28    31    35   次
累计驱逐量  172GB ..................................→ 1.96 TB
```

**占用被死死钉在 86~90%，从第一轮起就在持续驱逐。** mooncake 是近似 LRU、会误伤新键，
所以「某一轮自己写进去的 KV 能不能活到被读回」基本是运气——这就是 store 命中率
在 1%~24% 之间随机漂移的原因，而那恰好是我们要测的量。

这一轮之后，实验规程加了三条硬规则（见 [04 章](/notes/2026/08/25/2026-08-25-mooncake-store-kv-scheduling-04-conclusions-and-methodology/)）。

## 阶段六：换 qwen3-150b + 干净重测

三个前提全部堵死：多网卡按 NUMA 绑 rank、护栏改成相对累积量、**master 重启清空 store**
（700 GB 对 88 GB/臂 的工作集，7 倍余量）。加上 A B A B 交替 + 每轮查驱逐非零即中止。

### Config A（`GPU_BLOCKS=8000` = 512k token/P）

| arm | p50 | p90 | 本地 HBM | store | 重算 |
|---|---|---|---|---|---|
| aff_r1 | 2528.5 | 2970.9 | 90% | 2% | 7% |
| sco_r1 | 2538.5 | 2956.9 | 91% | 2% | 7% |
| aff_r2 | 2580.7 | 3002.2 | 91% | 2% | 8% |
| sco_r2 | 2569.7 | 2970.3 | 91% | 2% | 7% |

```
prefix_affinity    均值 2554.6 ms   重复间差 52.2 ms (2.0%)
cache_aware_score  均值 2554.1 ms   重复间差 31.2 ms (1.2%)
                   策略间差 0.5 ms (0.02%)   ← 比噪声小 40~100 倍
```

**无法分辨。** 全程 preemption none、Eviction 0/0。而且**有机制解释，不是巧合**：

```
prefix_affinity  : miss=1,  hit=405, 让位=27.5  → 偏离纯亲和 6.4%
cache_aware_score: miss=28, hit=406             → 偏离纯亲和 6.5%
```

两种完全不同的机制（硬阈值否决 vs 加权采样，`picked_argmax=0.95`）
达到了几乎相同的偏离率。既然偏离率相同、本地命中率相同，延迟自然相同。

### Config B（`GPU_BLOCKS=3000` = 192k token/P）

本地 KV 砍掉 62%，结果 HBM 90%→88%、store 2%→4%、**延迟一动不动**（2556 vs 2554 ms）。

为什么压小 HBM 没用——**两个约束的窗口不存在**：

```
每个 P 服务 24/7 = 3.4 个 trial，需常驻 3.4 个上下文
Config B 给了 192k / p50 46k = 4.2 个   ← 仍够装，命中率没掉
要迫使一半走 store，只能常驻 1.7 个 = 78k token = 1,220 block
但单个最长请求 87k = 1,360 block，两个并发要 2,720 block
                    ↑ 1,220 < 2,720，窗口是空的
```

根本原因是**单请求上下文与「节点需常驻的全部上下文」是同一量级（1 : 3.4）**。
这不是我选错了值，是这个比例决定的。

### 更根本的原因：每次 store 读本来就很便宜

```
Config A: store 2% × 46k = 920 token/请求   =  55 MB → RDMA 约 3 ms
Config B: store 4% × 46k = 1,840 token      = 110 MB → 约 5 ms
                                              对比 p50 = 2,556 ms → 占 0.2%
```

**提高 store 读的频率不可能产生可测效应，因为单次成本接近零。**
这一条把前面所有「测不出差异」的结果统一解释了。

### 一个副产品：Config B 的 mix 数据丢了又补回来

`campaign.sh` 里 `NODE_TAG=n1` 写死，而 Config B 的节点日志是 `_n2`，
于是 `run_policy.sh` 扫了旧日志、时间窗对不上，三列全变 0%。延迟（客户端侧）不受影响，
但丢的恰好是这轮唯一想看的变量。用 `recover_mix.py` 按时间戳聚类从 `p*_n2.log` 补算回来了。

## 阶段七：饱和实验

设计要点见 [05 章](/notes/2026/08/25/2026-08-25-mooncake-store-kv-scheduling-05-eviction-and-migration/)。一句话结果：
**驱逐扔掉 442 GB / 24 万 key，重算率一动不动，端到端只贵 0.6%**——
而这个「零损伤」恰恰暴露了实验设计本身的一个内在矛盾。

## 阶段八：Config C —— 收窄 store 带宽，补上「store 昂贵」那一侧

到阶段七为止，「store 便宜」这一侧已经测透了：5 轮实验、两个模型、两档 `GPU_BLOCKS`、饱和与非饱和，结论一致且有机制解释。但「store 昂贵」那一侧只有一个**被污染的**历史数据点——阶段一跨机单网卡那轮的 +27%，后来查明真因就是单口带宽卡住了 store 读。

Config C 补这一侧：`MC_DEVICE=mlx5_bond_0` 把 store 从每 rank 一张网卡（4 张）收成单张。自变量被隔离得很干净：

```
mooncake store  device_name = mlx5_bond_0        ← 唯一改动
blade-kvt       device_name = mlx5_bond_0..3     ← P→D 通道仍用 4 张，不受影响
```

7P+1D，`GPU_BLOCKS=8000`，4 臂交替，SEGMENT 保持 100GB：

```
arm            p50      p90      max   HBM  store  recomp      req
cnic_aff_r1  2423.9   2858.6   4690.6   91%     2%      8%  433/433
cnic_sco_r1  2424.0   2799.3   4295.1   91%     1%      8%  433/433
cnic_aff_r2  2426.9   2833.8   4431.2   90%     2%      8%  433/433
cnic_sco_r2  2448.2   2877.5   4273.2   91%     1%      7%  433/433

prefix_affinity    mean p50 = 2425.4ms  n=2  重复间差  3.0ms (0.1%)
cache_aware_score  mean p50 = 2436.1ms  n=2  重复间差 24.2ms (1.0%)
策略间差 +10.7ms (+0.44%) < 最坏重复间差 24.2ms  →  INDISTINGUISHABLE
```

全程零驱逐、零 preemption、`batch_put failed` 真实计数 0、`AllocFail=0`。对比 4 网卡基线（各臂 2397-2455ms）：**收窄网卡毫无变化。**

### 这是我事前就该算出来的

当年那个 +27% 需要**两个**条件同时成立：store 读贵 **AND** store 流量大。Config C 只补了前者——store 份额只有 1-2%，所以 4 倍慢的 store 读 = 0.8% 的端到端影响，仍在噪声里。**给一条只承载 2% 流量的通道降速，降多少都没用。**

> **顺带一个我自己制造的假数字**：监控里 `putfail=0` 全程显示为零，而那条管道以 `bc` 结尾——test1 上没装 `bc`，管道返回空字符串，再被 `${pf:-0}` 兜成一个很有说服力的 0。后来用 awk 真数了一遍，确实是 0，但那之前我读的是个空洞。**这是「假成功」清单里的第 8 个**，形状和前 7 个完全一样：某处静默失败，而唯一的症状是数字失去意义。

## 阶段九：Config D —— 第一次让 store 真正承担流量

Config C 说明必须补上「store 流量大」。用实测分布把窗口算清楚，结论是**这件事在 7P 下结构性做不到**。

### 窗口计算：约束是「最长单请求」，不是并发数

```
prompt_tokens  p50=46,150   p90=78,503   max=109,660   (max/p50 = 2.38)
blocks(64)     p50=721      p90=1226     max=1713
service p50 = 2.42s     duty@speed1 = 0.244

               每P常驻上下文   工作集      一半    最长单请求   窗口
7P (24 trial)      3.43       2472 blk    1236     1713     EMPTY by 28%
3P (24 trial)      8.00       5768 blk    2884     1713     OPEN  by 68%
```

要迫使约一半的复用走 store，`GPU_BLOCKS` 得压到工作集的一半；但它同时必须大于**最长的那个单请求**，否则最长的请求根本装不下。7P 下每个 P 只常驻 3.43 个上下文，一半（1236 blk）比单个最长请求（1713 blk）还小 —— 窗口是空的，而且**这跟并发数无关**。

这条推论值得单独记，因为它否掉了一个看起来很自然的做法：**调 `--speed` 对 7P 的窗口毫无帮助**。`--speed` 只改并发（think time），既不改工作集也不改最长请求。要打开窗口只能减少 P 节点数，从而提高每个 P 需要常驻的上下文数。

### Config D 的配置

```
TOPO=3p1d        每台 1 个 P（test1/2/3），D 在 test4，另两张卡闲置以保持 tp2 不变
GPU_BLOCKS=3000  = 192k token/P，工作集 5768 blk 的 52%，且 > 最长请求 1713 blk
SEGMENT=200GB    池 600GB，水位 540GB > 4 臂约 420GB
--speed 0.5      think 翻倍，把 conc/P 从 1.95 压回 1.11（接近 7P 基线的 0.84）
MC_DEVICE        保留 mlx5_bond_0 —— 两个条件第一次同时成立
```

`--speed 0.5` 是**放慢**（`delay = expovariate(1/7.5) / speed`）。以前担心的「speed 压缩会毁掉 store 命中」是 speed>1 的问题（异步 save 来不及落地），0.5 给的时间更多，方向相反。

### 结果：store 份额 19 倍，策略仍然无法分辨

```
arm            p50      p90      max   HBM  store  recomp      req
cd3p_aff_r1  2424.5   2945.7   7854.0   54%    39%      7%  433/433
cd3p_sco_r1  2424.6   2896.9   6434.6   53%    40%      8%  432/433
cd3p_aff_r2  2418.9   2898.8   7917.2   54%    38%      7%  432/433
cd3p_sco_r2  2437.5   3014.6   6426.6   49%    44%      7%  433/433

prefix_affinity     均值 2421.7ms  n=2  重复间差  5.6ms (0.2%)
cache_aware_score   均值 2431.1ms  n=2  重复间差 12.9ms (0.5%)
差 +9.4ms (+0.39%) < 最坏重复间差 12.9ms  →  INDISTINGUISHABLE
```

有效性检查是这条线里最干净的一轮：四个节点 `preempted=0` **且** `Preemptions: N reqs`
这个 gauge 的峰值为 0（364 个采样点的正面确认，不是「grep 不到」）、`batch_put failed` 0、
`AllocFail=0`、驱逐 0/0、store 354/600 GB 从未触水位、重算全程贴 8% 下界。

而且**噪声下限只有 0.2%，是这个项目里最好的一次**——分辨力约 6ms，实测差异 9.4ms 也仍在
重复间差之内。所以这次「测不出差异」不能归因于测量粗糙。

对比 Config C：

```
                       本地HBM   store   重算   p50        max
Config C (7P, 8000)      91%      2%     8%   2423.9ms   4690.6ms
Config D (3P, 3000)      54%     39%     7%   2424.5ms   7854.0ms
```

**store 从 2% 涨到 39%，端到端 p50 差 0.6ms。** 而重算仍贴在 8% 的理论下界，说明本地 HBM 丢掉的 37 个百分点被 store **完整接住**了，没有一点变成重算。preemption 全程为 none，所以 `GPU_BLOCKS=3000` 没有踩到那个「两个最长请求并发 = 3426 blk」的风险。

机制算得通，而且比阶段六那个 0.2% 的估算更彻底：

```
39% × 46k token ≈ 18k token，按 60 KiB/token ≈ 1.08 GB/请求要从远端 DRAM 读回
按 07 章 M4 实测的 28 GB/s  →  约 39 ms  =  2424ms 的 1.6%
```

（这个数有双重支撑：按单张网卡 200Gbps ≈ 25 GB/s 估是 43ms，而 M4 独立实测远端读
带宽 28 GB/s 给出 39ms。两个来源对得上。）

关键是这**不是「同样的 prefill + 额外传输」，而是「更少的 prefill + 更多传输」**：store 命中和 HBM 命中一样都省掉了那段 prefill，两者的差别只有 0 传输 vs 43ms 传输。**一次 store 读只值它所替代的那段 prefill 的约 2%。**

这把 cache-aware 调度的价值上界钉死了：它能赚的是 store-vs-HBM 那个差额（约 2%），而不是 store-vs-重算那个差额（那才是几百毫秒到秒级）。**真要有收益，必须是 store 也命中不了的场景**——而共享 store 的全部意义恰恰是让那种场景不发生。

唯一真正变差的是尾部：`max` 从 4690ms 涨到 7854ms（+67%），p90 +3%。那是单张网卡上偶发的长 store 读，说明带宽在尾部是真的紧了——只是它进不了 p50。
