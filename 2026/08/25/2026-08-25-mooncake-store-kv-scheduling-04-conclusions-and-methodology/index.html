04 · 结论与方法论

04 · 结论与方法论

1. 站得住的结论

以下 11 条都来自零驱逐 + 交替重复 + 双侧 preemption 检查的干净测量，
之前所有说法以此为准。

1. 几何前缀网格无害且必要。
141 个决策与线性网格逐一相同；1M 上下文下 key 数省 176 倍，索引表项从每请求 7,558 降到 43。
调度器 CPU 在 26k~85k 尺度量不出差异（都 <1s），收益要到长 prompt 才显现。

2. 指数打分 ≈ 修好的硬阈值。
在 store 充裕时无法分辨（0.02% vs 2% 噪声）。指数打分的结构性优势
（尺度无关、无「永不触发/永远触发」失效模式）仍然成立，只是无处兑现。

3. K = hit_weight/load_weight 太小确实更差（K=5 → 本地命中 66%，K=2.5 → 60%），
机制是采样偏离 argmax。方向可信，幅度不可信。

4. cache-aware 调度的收益取决于「选错节点的代价」，不取决于命中率高低。这一条现在是定论。
store 带宽充裕时这个代价是 0.2%，所以任何策略差异都被噪声吞掉。
之前测到的 +27% 真正来源是单网卡把 store 读卡住了，不是「亲和识别得更准」。

我们把这个代价推到了这套负载能达到的极限——Config C 收窄到单张网卡，Config D 再把 store
份额从 2% 推到 44%、节点数砍到 3 个——两个策略仍然无法分辨（+0.39%，噪声 0.5%）。
而这一轮的噪声下限只有 0.2%，是整个项目最好的一次，所以这不是测量粗糙。

价值上界有个干净的机制解释：store 命中和本地 HBM 命中省掉的是同一段 prefill，
两者只差一次远端读。按 M4 实测的 28 GB/s，39% 份额对应约 39ms，
是 2424ms 的 1.6%。所以调度能赚的是 store-vs-HBM 那个差额，而不是 store-vs-重算那个差额
（后者才是几百毫秒到秒级）。要有收益必须是 store 也命中不了的场景，
而共享 store 的全部意义恰恰是让那种场景不发生。

5. store 和本地 HBM 是完全的替代关系，不是叠加。
多轮实测：HBM 命中下降的百分点被 store 命中几乎等量接住，而重算量不变
（一直贴着 2/(N+1) 下界）。所以只要 store 还装得下，HBM 驱逐是无损的——
它只是把命中路径从「零成本」换成「几十毫秒的 store 读」。
Config D 把这条推到了极端：本地命中 91%→49%，掉的 40 多个百分点全被 store 接住，
重算率一动不动（7-8%，仍贴 8% 下界）。

6. 这个模型上「长上下文 → store 成本更高」不成立。
qwen3-150b 的 KV 密度是 Qwen3-32B 的 1/4（60 vs 256 KiB/token），
85k 上下文的每请求字节数（5.1 GB）反而比 26k 的 Qwen3-32B（6.4 GB）少。

7. 饱和本身几乎无代价，但这个结论有强前提。
驱逐扔掉 442 GB / 24 万 key，重算率仍贴着下界，端到端只贵 0.6%。
机制是「垃圾严格比工作集更旧」+「探测即续命保护活跃前缀」。
salt 隔离（为了对比干净而引入）恰恰制造了 LRU 的理想情况，所以这不能推广成
「近似 LRU 足够好」。

8. master 元数据压力的关键性质：lookup 只查本地未命中的那一段。
所以高本地命中率会自动保护 master。实测本地命中 90% 时只有 5,758 keys/s
（每请求 228 个 key，而非上下文对应的 1,437 个）。
风险不在实例数，而在「低本地命中 × 高吞吐」的组合——
也就是冷启动或缓存被打爆的时刻，恰好是最需要 store 的时刻。

9. GPU_BLOCKS 的可用窗口下界是「最长的那个单请求」，不是并发数。
要迫使一半复用走 store，GPU_BLOCKS 得压到节点常驻工作集的一半；但它同时必须大于
最长的单个请求，否则那个请求根本装不下。实测这套 trace：p50 721 blk、max 1713 blk。
7P 下每个 P 只常驻 3.43 个上下文，一半是 1236 blk < 1713 —— **窗口结构性为空**，
而且**调 --speed 对此毫无帮助**（它只改并发，不改工作集也不改最长请求）。
要打开窗口只能减少 P 节点数。3P 下常驻 8 个上下文，一半 2884 blk > 1713，窗口才打开。

10. 多 master 分区能突破单 master 天花板，而且代价比一开始以为的低得多。
实测 8 个 master 聚合 11.74M keys/s，是单 master 4.5M 的 2.6 倍，p99 反而从 4.77ms
降到 1.04ms。14M 的百实例外推需要 ≥4 个 master。

fan-out 在压测里付 50% 吞吐（N=8，且与 batch 无关），但那是压测器伪影：上限是
GIL 下的参数序列化（Amdahl f≈0.32，每进程 2.1M keys/s），而部署里每个 TP rank 是独立
进程、独立 GIL，即使百实例冷缓存外推也只用到每进程上限的 3.3%。所以部署里 fan-out 只剩
约 2ms 的查询延迟代价（p50 ×2.4），对 2424ms 的请求是 0.08%。
详见 07 章。

11. 分区的均衡性对冷数据成立、对热数据不成立，且热 key 的元数据无法分摊。
冷数据（24k blocks/臂）N=8 最坏偏差 1.9-2.3%；热数据（180 个共享前缀 block）
N=8 最坏偏差 29-47%，N=16 达 38-60%。后者是小样本问题，不随总量增长消失。
而且它没法用副本解决：一个 key 的元数据按定义只在一个 master 上，要分摊就得破坏
「owner = hash(key) 是纯函数」这个整个设计的立足点。只能绕开——减少探测量而非分摊探测。

2. 三个绝对基准（不会漂移，用来否定假结论）

这是本系列最有复用价值的部分。跨轮对比会被运行顺序、缓存预热、机器状态污染；
绝对基准不会。

基准一：重算下界 2/(N+1)

N 轮会话，所有 prompt 之和 = N(N+1)/2 单位，真正新增内容 = N 单位，所以

低于这个值的重算率一定是测量假象。 阶段四那个「重算 3%」在 8 轮下低于 22%，
物理上不可能——有了这个公式，同类假象能当场识破，不用等重跑。

基准二：噪声下限

同配置重复间差实测 1.2~2.0%。任何小于 2% 的策略差异在这套测量里不可分辨。
阶段四那个「领先 3.5%」本来就在噪声量级内，不该当成结论。

后来两轮的噪声比这小得多，分辨力因此更高：Config C 的 prefix_affinity 重复间差
只有 **0.1%**，Config D 是 0.23%。这一点很重要——它意味着后两轮「测不出差异」
不是因为测量粗糙。 Config D 能分辨约 6ms 的差异，而实测策略差异是 2.9ms。

3. 十个「假成功」陷阱：沉默不等于成功，回显也不等于成功

这十个都是我自己在编排或诊断里制造的，而且是同一类错误。

# bug 表现 修法
1 预热脚本没查 cp 退出码 cp 被 kill 后照样打印 PRELOAD_SHM_DONE，监控信了，实际只拷 8.3 GB / 280 GB 逐文件比对源/目标 size，全部一致才打印哨兵
2 ssh h 'cat > f && ... & disown' & 把整条 && 链塞进后台，cat 拿不到 stdin，脚本根本没写成，而 echo launched 照样打印 推送和启动拆两步，各自 md5 校验
3 HF_OVERRIDES={"..."} 在双引号 ssh 串里 远端 shell 剥掉内层双引号 → JSON 静默变非法 → 表现是「起来了但 max_model_len 还是 35840」 内层用单引号，并实测 json.loads 验一遍
4 campaign.sh 里 NODE_TAG=n1 写死 Config B 节点日志是 _n2，扫了旧日志时间窗对不上 → mix 三列静默变 0% 参数化；用 recover_mix.py 按时间戳聚类事后补算
5 管道以 bc 结尾，而 test1 没装 bc 管道返回空串，被 ${pf:-0} 兜成一个很有说服力的 putfail=0 用 awk/python 算数；别让默认值伪装成测量值
6 two_configs.sh 就绪检查写死 8 个端点 3P 拓扑下永远等不到 8/8，等满 20 分钟然后 abort 端点列表跟随 TOPO 推导，并回显期望数量
7 诊断用 grep -i preempt 匹配到 metrics 标签 Preemptions: 0 reqs，128 次「命中」看起来像大量抢占 匹配事件串要精确；顺带把检查改成读那个正面 gauge
8 用 free -g 判断容器内存 报的是宿主机（free=14GB），据此误判 master 被 OOM 杀死，而 cgroup 里 oom_kill=0、余量 143GB 读 /sys/fs/cgroup/memory.{max,current,events}
10 把压测器的上限当成系统的上限 单进程压测器在 2.1M keys/s 见顶（GIL 序列化），据此认定「客户端流水线是瓶颈」并排了一条 TODO；而部署里每 rank 独立进程，只用到 3.3% 任何「上限」都要先问：这是被测对象的性质，还是测量工具的性质？把它换算到部署的形态再看
9 M4 让 random 决定副本落位 1 副本落远端、2 副本有一份在本机（而 RDMA 下本机命中也走 transfer engine、不耗远端网卡）→「replica_num=2 更差」这个读数毫无意义 读回落位并拒绝采样到纯远端；客户端设 segment_bytes=0 免得热对象落进 reader 自己进程

第 3 个如果没提前测，8 节点铺开后极难归因——表现是服务正常启动、请求正常响应，
只有上下文长度悄悄不对。

第 5、7、8 三个值得单独说，因为它们不是编排 bug 而是诊断 bug：一个把默认值当测量值，
一个把标签当事件，一个从错误的来源读数。后果比编排 bug 更隐蔽——编排 bug 让实验跑不对，
诊断 bug 让跑对了的实验被读错。第 8 个尤其：那个错误诊断直接导出了一个「把 SEGMENT 降半」
的修复方案，去解决一个不存在的问题。

通用修法只有一条：校验状态，不信回显。 md5 对比、逐文件 size 比对、json.loads 实跑一遍。
而对诊断，还要多一条：优先找正面证据。「grep 不到抢占字符串」远弱于「Preemptions: N reqs
这个 gauge 在 364 个采样点上都是 0」。

4. 实验编排的七条硬规则

  1. 交替重复 A B A B，不是 A A B B。 运行顺序漂移必须被平均掉。
  2. 每轮查驱逐计数，非零立即中止整个 campaign——不是记录下来继续跑。
    一旦驱逐开始，后面所有数字都不可信，继续跑只是生产更多垃圾。
  3. store 预算是 arm 数的硬上限：每臂一个独立 salt 命名空间，
    7P 上每臂 88 GB → 4 臂 = 490 GB / 700 GB = 70%（安全），8 臂 = 980 GB（必然驱逐）。
    换拓扑要重算：Config D 是 3P、池 600 GB、每臂约 108 GB，4 臂 354 GB（59%，零驱逐）。
  4. 中止后重启必须换 arm label，否则第一个臂会命中自己上次的残留，
    表现是重算率低于 2/(N+1) 下界（grouping 那轮的 arm 1 就是这样，实测 4% < 8%）。
  5. preemption 双侧都查，而且读正面 gauge。 曾只 grep 7 个 P、漏了 D，而 D 侧有 111 条
    abort（1 个 D 承接 7 个 P 的流量，配额需求是单个 P 的 7 倍）。另外「grep 不到 preempted」
    是用缺失当证据；Preemptions: N reqs 这个 gauge 才是正面确认，Config D 靠它拿到了
    364 个采样点的零抢占。
  6. 验证服务存活用端口连通性，不用 pgrep -f。
    pgrep -cf "mooncake_master" 会把自己那条 ssh 命令串也算进去，返回 1 →
    误判「已在运行」→ 跳过启动 → 8 个 P 全在 assert store.put() 上失败。
    用 timeout 3 bash -c 'echo > /dev/tcp/HOST/PORT'。
  7. salt 隔离而不是重启集群来做策略对比。但注意它有副作用，见 05 章。

5. 一个省时间的做法

先离线模拟再跑真集群。 stub 掉 aiohttp 直接 exec scheduler.py，
用假 ClusterState 模拟 24 trial × N 轮 × 7 节点（含共享系统提示），
几秒钟就能看出分配是否拉平。真集群一轮 5 分钟，模拟能挡掉无效方案。

注意 stub 时要先 sys.modules["<name>"] = module 再 exec，否则 @dataclass
会因找不到模块而报 AttributeError: 'NoneType' object has no attribute '__dict__'。

实测 ratio=3.0 在模拟里就能复现旧护栏的病态（56/0，3 个节点闲置），
不用上集群就知道它不行。
